# Scout's reproducible setup, and how to recover it

This directory is the export of *how Scout is configured* and *where it is right now*. It is
inspectable configuration and point-in-time state — not a backup, and not a second copy of the
project's code.

| file | what it is | regenerated by |
| --- | --- | --- |
| `versions.json` | runtime identity (Hermes version, upstream revision, install method, Python) and every local customization, with an observation time | `python3 scripts/scout-snapshot.py` |
| `config-export.json` | **allowlisted** non-secret configuration fields, and the list of fields that were not set | same |
| `STATE-SNAPSHOT.md` | schedules, budget, live resources, destinations, queue, recovery notes — each with its authoritative source | same |

`python3 scripts/scout-snapshot.py --check` verifies the committed exports are present and carry no
secret-shaped string. It runs in CI.

## What lives in Git, and what does not

**In Git (this repository):** the scripts, skills and worker modules that *are* the project; the
release policy and per-dataset licence declarations; the release packages and their manifests; the
handoff and operational documentation; these exports.

**Provider-managed, deliberately not in Git:** the Hermes image and version (the platform updates
it), the machine lifecycle and billing, the dashboard, and the subscription. The installed runtime
is Docker-managed under `/opt/hermes` and must not be self-updated; only `/opt/data` survives a
restart.

**Never committed anywhere in this repository:** `.env` files, token or auth stores, SSH private
keys, raw conversations or tool logs, full memory dumps, live SQLite databases (including
`state.db`), browser profiles, and any secret-bearing archive. The exports record credential
*names and paths only* — never values. The snapshot script refuses to write a file containing a
secret-shaped string and refuses to include a file whose extension is in the forbidden list.

## How secrets are supplied

Two mechanisms, both out of band:

1. **Dashboard environment** (`/opt/data/.env`, mode 0600): the operator writes variables on the
   Env page. These reach the agent process, not necessarily a terminal subprocess.
2. **Credential files** (`/opt/data/.secrets/`, mode 0600), exported as `*_FILE` paths by
   `scripts/scout-factory`: `hetzner.token`, `github-staging.token`, `github-publish.token`,
   `huggingface-write.token`.

Names that matter, and the distinction between them:

| name | role |
| --- | --- |
| `HCLOUD_TOKEN_FILE` | Hetzner API for worker lifecycle and the cleanup sweep |
| `FACTORY_GITHUB_TOKEN_FILE` | staging repository (worker artifacts) |
| `FACTORY_PUBLISH_TOKEN_FILE` | the dataset's own GitHub repository (wider than staging) |
| `FACTORY_HF_WRITE_TOKEN_FILE` | **publishing** to Hugging Face (`HF_TOKEN_WRITE`) |
| `HF_TOKEN` | **inference only** — never used to publish, and its configuration is not changed by the publishing path |

## Recovering this setup

1. **Read the state before touching anything.** `STATE-SNAPSHOT.md` carries the queue, the next
   action, the budget and the live resource count, each with the command that produced it.
2. **Reconcile live resources and spend.** List the worker ledger (`jobs/*.json`) for records whose
   status is not `deleted`, then run `python3 scripts/provider-inventory.py` and compare against the
   provider. Collect and destroy anything the ledger still owns.
3. **Reconcile the schedule.** `hermes cron list` should show exactly the jobs in
   `STATE-SNAPSHOT.md`. Everything scheduled is script-only and idempotent; nothing needs to be
   re-created from this description.
4. **Re-register skills if the runtime was rebuilt.** They load through `skills.external_dirs`
   (`dataset-factory/skills`), which is recorded in `config-export.json`; the skill sources are in
   this repository at `skills/`.
5. **Refresh the export** after a meaningful configuration change:
   `python3 scripts/scout-snapshot.py`, then commit. The weekly digest does not need to regenerate
   it; the routine does it when configuration changes.

## What restoring this description must NOT do

- **Do not enable a second coordinator.** Exactly one process may write the worker ledger and
  launch workers; a second one duplicates jobs and double-spends.
- **Do not create duplicate cron jobs.** The schedule in `STATE-SNAPSHOT.md` already exists on the
  instance; re-creating it produces double sessions, double digests and a breached session cap.
- **Do not reset the allowance accounting.** The worker allowance is summed from the reservation
  recorded in each `jobs/*.json` record, and the research allowance is measured from Hermes's own
  usage ledger. Deleting records or clearing usage to "start clean" silently resets both.
- **Do not change inference authentication to fix a publishing problem.** The publishing
  credential is `HF_TOKEN_WRITE`; `HF_TOKEN` stays inference-only.

## Scope

This is a description of a running system, not a bootstrap kit. It is enough to resume the work, to
understand what is configured and why, and to reconcile the live state — without re-creating
anything that already exists.
